# Milestone v0.1: Game.ini Integration (SUPERSEDED)

**Status:** SUPERSEDED 2026-01-25
**Phases:** 1-3
**Total Plans:** 7

## Overview

Initial implementation using Game.ini as source of truth with staged-changes model. This architecture was superseded before shipping due to a pivot to database-driven configuration where the web app becomes the authoritative source.

## Why Superseded

The Game.ini-based approach had limitations:
- Game mod couldn't request config on startup (needed to read from web app)
- Bulk weapon selection UI was complex for users
- No persistence of uncommitted changes
- Eager loading of all configs

The new architecture (v1.0) uses:
- Web app JSON files as source of truth
- Working state → Save → Apply flow
- Accordion-based weapon selection (one at a time)
- Lazy loading per weapon/category
- API endpoints for mod startup integration

## Milestone Summary

**Key Decisions:**
- Used new-york style for Shadcn UI (cleaner aesthetic)
- Store tracks staged state per config key (not per value)
- All input components use consistent prop interface: { value, onChange, disabled }
- Multi-weapon editing applies changes to ALL selected weapons
- Parser skips unknown config keys (not in schema)
- Single RCON connection for batch commands with 100ms delay
- Vector2D formatted with Z=0.00 suffix per game mod requirement

**Issues Resolved:**
- Turbopack CSS resolution (copied tw-animate-css locally)
- General_ prefix not handled in weapon config key parsing
- Stale staged changes at apply time (get fresh state in click handler)

**Issues Deferred:**
- None (milestone superseded before shipping)

**Technical Debt:**
- ConfigRow and CollapsibleSection in weapons/ could be moved to shared/
- Some hardcoded animation values in globals.css

**What Carries Forward to v1.0:**
- Next.js/Tailwind/Shadcn foundation
- Input components (BooleanInput, FloatInput, VectorInput, Vector2DInput, FloatArrayInput)
- RCON connection logic (formatters need updating)
- Schema definitions
